# 職涯規劃

## 為什麼做

使用者會問：「**我離想要的工作還差什麼？要先補哪些？**」

面試練習解決「怎麼講」，職涯規劃解決「**能力夠不夠、缺什麼、怎麼補**」。

## 做法

履歷（必填）＋個人檔案（選填：自我介紹、想做的職務、地點、薪資）→ **比對使用者自己的目標職缺** → 這些職缺共同要求什麼、你缺什麼 → 準備度分數、優勢、能力缺口、準備計畫（大項目和可以打勾的小項目）。

- **有目標職缺**：缺口依目標職缺的實際要求判斷，最準。每個目標職缺會有契合度和補強點。
- **沒有目標職缺**：依想做的職務和一般常見要求推估，並提醒使用者加入目標職缺後重新分析。

### 讀取 GitHub 作品集

以前作品集連結只把「網址文字」放進 prompt，AI 根本沒有讀到內容，分析只依履歷。現在分析前會先由後端實際讀取：

1. **讀 repo**（[github.py](../../backend/app/modules/career/github.py)，只連 `api.github.com` 與 `raw.githubusercontent.com`）：基本資訊、語言比例、README、**完整目錄**、設定檔（requirements、package.json、Dockerfile、compose、CI workflow⋯）、**主要原始碼**（依路徑挑商業邏輯所在的檔案，例如 service、agent、worker、pipeline，並分散到各資料夾，再加 1–2 個測試與 1 個 migration）、最近 30 個 commit。每個 repo 約讀 20–35 個檔案、10 萬字。
2. **逐一深入審閱**（reasoning 模型，每個 repo 一次、同時進行）：在做什麼、架構、技術、**每項能力都附檔案路徑當證據**、工程實務、面試亮點、可補強處、完成度。不是一句話摘要，整份審閱結果都會交給職涯分析。
3. **職涯分析引用作品集**：優勢要引用作品集的具體證據；作品集已證明的能力不能列為缺口；作品集的可補強處若跟目標職缺有關，變成缺口或準備小項目並指名 repo。
4. **攤開依據**：每個連結旁標示「已讀取 N 個檔案／讀取失敗（原因）／未讀取」，結果頁有「Ava 從你的作品集讀到什麼」，可以展開看審閱內容和讀了哪些檔案（點了直接開 GitHub）。

規則與限制：
- 只讀 GitHub 公開 repo。私人 repo、不存在、非 GitHub 網址會標出原因，不當作證據，也不影響整份分析。GitHub 個人頁（`github.com/帳號`）只讀 repo 清單，不讀原始碼。
- 一次最多深入讀 `PORTFOLIO_MAX_REPOS`（預設 5）個 repo；每個連結最多 200 秒，逾時就略過。
- 審閱結果依 commit 快取 7 天：程式碼沒變就不重新花錢審閱。
- GitHub API 沒設 `GITHUB_TOKEN` 時整台伺服器每小時 60 次（約 5 次分析），正式環境一定要設。被限流時改用該 repo 最近一次讀到的結果（30 天內），畫面會註明。

### 歷次分析

每次「重新分析」都會保留一份，打勾進度各自保存。結果頁的「歷次分析」可以切換到任何一次（顯示當時的準備度與缺口數），看舊的分析時上方會提示並可以「回到最新」。每份分析顯示的是**當時**的個人檔案與作品集讀取結果。

### 為什麼不上網搜職缺

之前的版本會先用 AI 即時上網搜尋職缺（104、CakeResume），再拿來比對。問題是：

- 搜到的職缺品質不穩：可能過期、不相關、只是列表頁；104 有機器人驗證，網址也確認不了。
- 職缺不準，算出來的缺口就跟著偏，整份建議不可信。
- 很慢（約 3 分鐘）也很貴。

改成用使用者自己挑的目標職缺：資料最可靠，分析約 15 秒，也跟產品核心「針對目標職缺準備」接在一起。

## 怎麼用

1. 職涯規劃頁選分析用的履歷（**必填**，要解析完成），其他欄位（自我介紹、想做的職務等）都是選填，填越多越準。
2. 按「儲存並開始分析」。沒有作品集約 30 秒；有 GitHub 作品集要先讀原始碼，約 1–2 分鐘。
3. 照準備計畫一項一項打勾。
4. 加入新的目標職缺、更新履歷後，按「重新分析」。

## 怎麼測試

**功能**
- 沒有履歷、履歷還在解析、履歷解析失敗 → 「開始分析」不能按，旁邊說明原因；直接呼叫 API 也會被擋。
- 只上傳履歷、其他欄位都不填 → 可以完成分析。
- 有目標職缺 → 「你的目標職缺」列出每個職缺的契合度、補強點，按鈕可以回到目標職缺頁。
- 沒有目標職缺 → 顯示「還沒有目標職缺」和「貼上職缺內容」按鈕。
- 小項目打勾後重新整理還在。
- 作品集填公開 repo → 連結旁顯示「已讀取 N 個檔案」，「Ava 從你的作品集讀到什麼」能展開看審閱與檔案清單；填私人或不存在的 repo → 顯示「讀取失敗」與原因，分析照常完成；填非 GitHub 網址 → 顯示「未讀取」。
- 分析兩次以上 → 出現「歷次分析」，切到舊的會顯示提示與「回到最新」；在舊的分析打勾不影響最新那份。

**效果**
- **缺口要對應職缺**：例如 Python 背景的人比對 Go＋Kubernetes 的職缺，缺口應該出現 Go、Kubernetes，契合度偏低。
- **不能捏造經歷**：履歷沒寫的技能，不能被列為優勢。
- **作品集要真的被讀到**：優勢應該出現 repo 名稱和具體做法（例如「AI_Interview 用 outbox＋arq 做背景工作重試」），不是只有技術名詞；repo 裡有 tests/ 就不能說沒有測試。
- **準備計畫要能執行**：小項目是具體行動（例如「用 Docker 包 Django 專案」），不是「加強雲端能力」這種空話。
