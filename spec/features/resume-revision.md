# 履歷修改

> 程式裡的模組、API、資料表叫 `revisions`（`/resume-revisions`、`resume_revisions`），畫面上叫「履歷修改」，網址 `#revise`。

## 為什麼做

使用者常說「我其實還做了很多事，只是履歷沒寫」。但直接給一個輸入框問「你還做了什麼？」，大多數人寫不出來：
不記得自己做過什麼，也不知道哪些值得寫。

所以這個功能不是「AI 幫你潤飾文字」，而是**由 Ava 拿你的履歷去對照職缺，主動問出具體的問題**，像語言學習 App 開始前的卡片一樣，一關一關、大多點一下就能回答，最後才產生新的履歷。

## 怎麼用

側欄「履歷修改」→ 開始。整個流程約 3–5 分鐘，分三個階段：

### 階段 A：設定（固定的卡片，全部用點的）

1. **這次要改來做什麼？** 投特定職缺／整體更新／轉職／第一份工作
2. **用哪份履歷**：預設主要履歷，要解析完成才能用。
3. **確認卡**：「Ava 讀到你是 3 年後端工程師、主要用 Python⋯對嗎？」能從履歷讀出來的就不再問，只請使用者確認；不對可以補一句修正。
4. **要投哪個職缺**（選填，0–3 個）：選了才會依職缺要求去修，沒選就做整體改善。可以直接貼新職缺。
5. **GitHub 作品**（選填）：輸入 GitHub 帳號 → 列出最近更新的公開 repo（不含 fork）勾選，最多 5 個；也可以直接貼 repo 網址。
   會先帶入「能力落差分析」填過的作品集連結。
6. **輸出偏好**：中文／英文、一頁／兩頁

### 階段 B：挖掘（Ava 依你的履歷產生 6–10 張卡）

有勾 GitHub 作品時，產生卡片前會先在背景**實際讀原始碼並審閱**（沿用能力落差分析的讀取與審閱：README、完整目錄、設定檔、主要原始碼、最近 commit，每個 repo 約 1–3 分鐘，依 commit 快取 7 天）。
等待畫面會寫正在讀哪些 repo，可以先離開。讀完後：
- 每個讀到的 repo 一張**作品卡**排在最前面：「Ava 讀了 X 的 25 個檔案：在做什麼⋯要寫進履歷嗎？」選項是「加進去，我自己做的」「加進去，團隊一起做的」「不要放」，要放的可以補成果（使用者數、上線）或負責的部分。作品卡由程式產生，不交給模型，才不會漏掉。
- 程式碼已經證明的技能不會再出缺口卡問。讀不到的 repo（私人、不存在、被限流）不出卡，結果頁會寫原因。

| 卡片 | 例子 | 回答方式 |
|---|---|---|
| 缺口卡 | 「職缺要 CI/CD，你的履歷沒提到。你做過嗎？」 | 選項；選了「有」才展開細節 |
| 量化卡 | 「你寫『優化 API 效能』，大概快了多少？」 | 選範圍或填數字 |
| 遺漏卡 | 「最近一年有沒有沒寫進去的專案？」 | 直接打字 |
| 釐清卡 | 「『負責後端開發』是你一個人做，還是帶團隊？」 | 選項 |
| 刪減卡 | 引用一段原文：「這條可能已經過時：熟悉 jQuery、Flash」 | 刪掉／縮成一句／保留 |
| 想刪的部分 | 最後一張：「還有想刪掉或縮短的部分嗎？」 | 用一句話說，例如「作品集只留前兩個」 |

- 先補再刪：缺口 → 數字 → 角色 → 漏寫 → 刪減，最後一張讓使用者自己用自然語言說要刪哪裡（某段經歷、作品集、整個區塊）。
- 刪減卡 1–3 張，依[初篩檢核表](../../backend/app/ai/knowledge/resume_screening.py)挑最可能拖累初篩的內容：過時技術、跟目標無關的舊經歷、重複、填充詞、敏感個資。Ava 只提出，刪不刪由使用者決定。
- 先選再寫：選了代表「有」的選項才展開輸入框，只問一層。
- 輸入框下面有範例句，讓使用者知道要寫到多具體。
- 每張都可以跳過；進度條在上面；每答一張就存，中途離開回來會接著上次那張。
- 沒選職缺時不會出缺口卡，改成依「這次要改來做什麼」問。

### 階段 C：產生結果

- 新版履歷逐條標出改動：**新增**（來自你第幾題的回答）、**改寫**（附原文與理由）、**刪除**（刪除線＋理由，可以「保留這條」）、沒動的照原樣。
  原履歷的內容不會默默消失：選了刪掉的、使用者自己說要刪的、一頁放不下的、敏感個資，都用「刪除」標出來。
- 每條改動都可以接受或還原，也可以直接改文字。
- 選了要放的 repo 寫成「專案」區塊的一項：做了什麼、架構與技術、工程實務，都用程式碼審閱裡的證據；使用者數、上線這類程式碼看不出來的成果只來自使用者的回答。選「不要放」或跳過的 repo 不會出現。
- 結果頁最下面列出「Ava 讀了你的 GitHub」：每個 repo 讀了幾個檔案、沒讀到的原因。
- 不捏造：使用者沒給的數字留成 `[多少用戶？]` 這種待補標記，匯出前會提醒還有幾個沒填。
  缺口卡選「沒有」的技能不會加進履歷，結果頁會建議去「能力落差分析」補。
- 輸出：**下載 Word**、**複製文字**、**存成新的一份履歷**（原本那份不動，可以順便設為主要履歷；存了之後會像上傳的一樣解析，面試、題庫都能用）。
- 完成頁的主要按鈕是「用新履歷練一場面試」：履歷上寫了，面試就會被問到。

### 初篩檢查（結果頁最上面）

新版產生後自動再跑一次審閱（之後可以按「重新檢查」），用兩個角色判斷會不會在第一關被刷掉：

| 角色 | 看什麼 |
|---|---|
| HR／招募 | 前 6 秒印象、職缺關鍵字、完整度（日期、聯絡方式）、篇幅、紅旗（空窗、頻繁換工作、錯字、前後不一致） |
| 用人主管 | 相關性、成果有沒有量化、角色、技術深度、有沒有讓人想約面試的亮點 |

- 結果：初篩判斷（大概率通過／邊緣／很可能被刷）＋理由、原履歷與新版的分數、HR 前 6 秒印象、職缺關鍵字有寫到幾個、還要改的地方（依嚴重程度排序，指到某一條的可以點了直接跳過去編輯）。
- 兩層判斷，標準才固定：
  1. **檢核表**（[resume_screening.py](../../backend/app/ai/knowledge/resume_screening.py)）：HR 與用人主管看什麼、可以刪減的內容、市場標準。中文履歷用台灣（104、新創）的標準，英文履歷用外商的標準。刪減卡、產生新版、初篩檢查都用同一份。
  2. **程式檢查**：程式查得準、AI 容易漏看的項目直接用規則查（關鍵字有沒有出現、篇幅、經歷有沒有日期、還有沒有 [待補]、Email、身分證字號／生日／婚姻狀況、填充詞），結果交給 AI 一起判斷，也直接列在「格式檢查」。
- 使用者改過履歷後，面板會提示「重新檢查」。

歷次修改都會保留，在「履歷修改」首頁可以點回去看。

## 為什麼這樣設計

- **問題由 AI 依履歷＋職缺產生，不是固定問卷**：固定問卷問不到點上；比對職缺要求才知道「該問什麼」。
- **卡片一次只問一件事、大多用點的**：降低開始的門檻，完成率比一個大表單高。
- **選了職缺才依職缺修**：沒選時硬套「常見職缺要求」會把不相干的技能塞進履歷。
- **存成新的一份，不覆蓋**：使用者可能針對不同職缺各存一份。

## 怎麼測試

**功能**
- 沒有解析完成的履歷時不能開始；選了還在整理的職缺會被擋。
- 答到一半重新整理，會回到下一張還沒答的卡；跳過的卡不會被當成「沒有」。
- 接受／還原／編輯後，下載的 Word 和複製的文字都是目前的版本。
- 存成新履歷後，履歷清單多一份，原本那份不變；超過履歷份數上限會被擋並提示。

- 勾了 GitHub 作品：等待畫面顯示正在讀 repo；作品卡選「不要放」的 repo 不會出現在新版履歷；重試時不會重讀。
- 貼 GitLab 等非 GitHub repo 網址會被擋。

- 刪減卡選「刪掉」的那段在新版是刪除線，Word 裡沒有；按「保留這條」後回來。
- 初篩檢查會自動出現；改過履歷後提示重新檢查，重新檢查後提示消失。

**效果**
- 缺口卡要對應職缺真的有寫、履歷真的沒寫的能力，不能問履歷已經寫了的東西。
- 新增的內容都要能追溯到某張卡的回答；回答「沒有」或跳過的，不能出現在新履歷。
- 使用者沒給的數字不能自己編，要留待補標記。
- 刪減卡只針對真的可能拖累初篩的內容，不能對重點經歷出卡。
- 初篩分數要誠實：新版沒有比較好就不能硬給高分；必改清單要能執行，不能只寫「可以更好」。
- GitHub 專案的描述要具體到架構與技術（例如「用 outbox＋arq 做可靠的背景工作」），不能只寫「熟悉 Python」，也不能寫程式碼裡沒有的東西。
